# .NET 与 Unity

托管程序集通常保留丰富的类型和元数据，因此比原生程序更容易阅读，但发布模式、混淆、ReadyToRun、NativeAOT 和 Unity IL2CPP 会显著改变分析方式。

## 普通 .NET 程序集

优先用 ILSpy 浏览 Assembly、命名空间、类型、方法、属性、资源与 IL。需要 Windows 下动态调试或编辑程序集时，可评估仍在维护的 dnSpyEx。

建议流程：

1. 记录程序集哈希和目标运行时版本。
2. 检查入口点、引用程序集、资源和配置文件。
3. 从 UI 事件、命令处理、序列化模型或独特字符串定位业务逻辑。
4. 将反编译 C# 与 IL 交叉验证，尤其关注泛型、async/await、迭代器和异常处理。
5. 运行时验证仅在隔离且获准的环境完成。

反编译导出的项目不一定能直接构建：编译器生成结构、缺失依赖、资源和条件编译信息可能无法恢复。

## 判断是否为托管程序集

可检查 PE 的 CLR/CLI 数据目录，或使用 `file`：

```bash
file target.exe
```

托管程序集的输出中通常带有 `Mono/.Net assembly` 标记。注意 `file` 只读取文件头，单文件打包或 NativeAOT 的结果可能显示为普通 PE，需要结合导入表或 CLR 数据目录进一步确认。

如果 ILSpy 无法正常解析，不要立即认定文件损坏；它可能是原生程序、单文件打包、NativeAOT、混淆结果或只包含本地启动器。

## Unity

### Mono 后端

常见代码位于 `Managed/Assembly-CSharp.dll`，可用 ILSpy/dnSpyEx 阅读。资源和场景是另一条分析线，不应与程序集代码混为一谈。

### IL2CPP 后端

C# IL 会被转换为 C++ 后编译成本地机器码。通常需要结合：

- 原生二进制（如 `GameAssembly.dll` 或平台对应文件）；
- `global-metadata.dat`；
- Ghidra/IDA 等原生分析工具；
- 与具体 Unity/IL2CPP 版本匹配的获准研究工具。

IL2CPP 下恢复的类型名、方法映射和伪代码仍需动态证据验证。

## 修改程序集的边界

程序集编辑会改变哈希和签名，可能破坏强名称、Authenticode、完整性校验、更新机制或服务端协议。修改只应发生在测试副本中，并记录原始文件、补丁内容和恢复方法。不要分发含第三方版权代码的修改程序集。
