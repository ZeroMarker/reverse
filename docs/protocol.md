# 协议与网络分析

本章讨论自有或获准分析的目标程序的网络行为：理解它使用什么协议、如何封包与解析，以及如何验证结论。只分析你拥有或明确获准的流量与设备；在未授权的账号、网络或服务上抓包与重放可能违反法律和服务条款。

## 先从静态入手

网络行为在静态分析中往往已可见：

- 导入 API：`connect`/`send`/`WSASend`、`getaddrinfo`、TLS 库（OpenSSL、Schannel、BoringSSL）等；
- 独特字符串：域名、URL 路径、用户代理、协议魔数、错误消息；
- 配置与资源：内置端点列表、证书、`networkSecurityConfig`（Android）或嵌入的公钥；
- 解析函数：围绕长度前缀、定界符、TLV 结构和状态机定位封包/解包代码。

先建立"程序应该发什么"的假设，再抓包验证，比对着抓包结果盲目猜协议效率高得多。

## 抓包环境

按[标准分析流程](workflow.md)第 2 步搭建隔离网络：受控 DNS、模拟 HTTP 服务和完整流量记录。常用命令：

```bash
# Linux 上捕获（在隔离网络中进行）
tcpdump -i any -w capture.pcap

# 读取与过滤
tshark -r capture.pcap -q -z conv,tcp
tshark -r capture.pcap -Y "tcp.port == 443" -T fields -e frame.number -e ip.dst -e tcp.len
```

明文协议（HTTP、自定义 TCP/UDP）可直接在 Wireshark 中跟踪流重组。注意：抓到的流量只是程序行为的一个子集，重试、条件分支和未触发的路径都不会出现。

## TLS 流量

- **控制客户端信任**：在测试设备上安装你自己的 CA。Android 7+ 应用默认不信任用户 CA，除非其网络安全配置允许；Windows 可用组策略或浏览器导入。
- **mitmproxy** 适合交互式查看和改写 HTTP(S)：

```bash
mitmproxy --mode regular --listen-port 8080
mitmdump -w flows.dump --set flow_detail=2
```

- **证书绑定（pinning）**：应用可能校验服务器证书指纹。在自有测试构建中修改校验逻辑或配置是首选方式；对别人的发布版本做绑定绕过需要明确授权，且不要把来源不明的绕过脚本直接用于真实设备。
- 双向 TLS（mTLS）需要客户端私钥，仅当你拥有它时才能解密流量。

TLS 密钥日志（如 `SSLKEYLOGFILE`）只对你控制的环境有效，记录后必须按授权要求保管和销毁。

## 重建协议

1. 确定传输层边界：TCP 需要处理粘包/分包，先找长度前缀或定界符；UDP 通常一包一消息。
2. 标注字段：魔数、版本、长度、序号、校验和、时间戳、载荷。字节序和位域容易出错，用汇编或反编译结果确认解析端的实际读法。
3. 用多种输入重复实验，区分固定值、会话相关值和随机值。
4. 用[声明式格式描述](tools.md)（如 Kaitai Struct）把结论固化为可执行的解析器，解析器与实际流量不一致时回到第 2 步。
5. 重放实验只针对你自己的服务端或测试环境；重放可能触发不可逆操作（下单、删除、告警）。

## 常见误区

- 域名或 IP 出现在字符串里不代表该路径一定会执行，必须有调用关系或运行证据。
- 抓包结果与代码对不上时，优先怀疑解密、压缩、序列化库版本和代理环境差异，而不是急于修改结论。
- 混淆或自定义"加密"常只是异或、置换或字典编码，先做熵和字节分布检查再下结论。
- 时间戳、随机数和校验和字段会在重放时暴露"复制粘贴式"伪造的客户端。
